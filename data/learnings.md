## 2026-09-28 オーナーから受けた方針

**ジャンルはバランスよく回す。ただし1本ごとの品質をできるだけ高くする。**
「いまのAIのすごさを実感してほしい」とのこと。数をこなすより、1本の完成度で驚かせにいく。

(※ 2026-09-28 追記: このあと目安は400行→**1500行**、土曜のみ**5000行**に引き上げられた。
ただし下に書いた「密度で品質を出す」考え方は変えない。行数はあくまで結果。)

品質は行数ではなく**密度**で出す。具体的には:

- **効果音をつける**: Web Audio API で波形を合成すれば、外部ファイルなしで音が出せる。
  無音か有音かは体感差が大きいので、費用対効果が最も高い。
- **手触りを作り込む**: 当たった瞬間の画面揺れ、取ったときのパーティクル、
  イージングのかかった動き。1つ数行で入る割に印象が変わる。
- **難易度カーブを設計する**: 序盤で操作を覚えさせ、中盤で要素を足し、終盤で密度を上げる。
  1本目の「さかさロケット」は後半が単調という反省が出ている。
- **タイトル画面と結果画面まで作る**: 遊び終わったあとの余韻まで含めて1本とみなす。

判断に迷ったら「凝った仕組み1つ」より「丁寧に仕上げた素朴な仕組み」を選ぶ。

1周したらまた1に戻る。同じジャンルが回ってきたら、テーマと操作は必ず変える。

**土曜公開ぶん(大作枠)はローテーションの外に置く。** ジャンルは自由で、遊べる時間は長いほど良い

例: 9/30 シューティング → 10/1 リズム → 10/2 物理 → **10/3 大作(自由)** → 10/4 タイムアタック → 10/5 ローグライク

### 3Dも混ぜる

外部ライブラリが使えないので、3Dは自前で描く。使える手が3つある。

- **擬似3D路面**: 遠くの線を細く・速度を落として描く。レース向き。実装が軽い。
- **レイキャスティング**: 1本ずつ光線を飛ばして壁の高さを出す。迷路・ローグライク向き。
- **ワイヤーフレーム**: 頂点を透視投影して線で結ぶ。シューティングの敵や地形向き。

1周6本のうち**2本を擬似3D**にする。まずレースとシューティングで試し、
うまくいったらローグライクのレイキャスティングに進む。残りは2Dで確実に仕上げる。

### ローグライクについての但し書き

目安が1500行(土曜は5000行)になったので、以前ほど窮屈ではない。それでも要素は絞る
(8〜10フロア / 敵3〜4種 / アイテム4〜5種)。
「広さ」ではなく「1回の判断の重さ」で面白さを出す方針は変えない。
行数に余裕ができたぶんは、階層生成の質と演出に使う。

## 2026-09-28 行数の目安を引き上げ、土曜に大作枠を作った

オーナーの指示は2段階で来た。最初が「1000行ぐらいまで上限上げていい。全部」、
そのあと「基本を1500行上限に変更して、土曜日は5000行上限にした大作を作成するようにして」。
最終的にこうなった。

| | 目安 | テストの強制上限 |
|---|---|---|
| ふだん | **1500行** | 1800行 |
| **土曜公開ぶん(大作枠)** | **5000行** | 6000行 |

強制上限を目安の2割増しにしているのは、ギリギリで落ちて出荷できない事故を防ぐため。
`tests/game.spec.ts` はフォルダ名の先頭10文字(公開日)から曜日を出して、
土曜なら自動で大作枠の上限に切り替える。ボクが申告する必要はない。

**「土曜」は公開日で判定する**(作るのは前日の金曜夜)。
週末に時間のある人に遊んでほしいので、公開日基準にした。

あわせて、遊べる長さのルールも変えた(こちらも2段階):
「1〜3分で1プレイが終わる」→「1プレイ1〜3分で通算20分」→ 最終的に
「**通算30分以上。遊ばせ方はゲームごとに自分で決める**」。
オーナーの言葉は「5分をたくさん、30分を一回、15分を2回とか、マジで任せる」。
さらに後から「30分は目安であって、そこまで気にしなくていい。たくさん遊んでもらえるならそれはいいこと」。
**30分に届かないことを理由に水増ししない。** 逆に、面白くて長く遊べるなら上限は気にしない。

**ただし、行数を使い切ることを目標にしない。**
芯を1つに絞る、という前提は変わっていない。
「さかさロケット」が378行、「ひかりのかけら」が384行(どちらも削除済み)で成立したのは、
芯が1つに絞れていたから。長くしたら面白くなるわけではない。

増やしていいのは、次のような「必要があって増える」ぶん:

- 擬似3Dやレイキャスティングの描画処理
- ローグライクの階層生成とアイテム処理
- 効果音の種類、演出、難易度カーブの作り込み
- チュートリアル的な最初の1面

判断基準はひとつ。**その行数が増えた理由を devlog で1文で説明できるか。**
説明できないなら、それは膨らんだだけなので削る。

長くなるほどテストで落ちる確率が上がり、出荷できない日が出る。
そのリスクを負うだけの中身があるか、毎回自問する。

### 通算30分遊ばせるために効くこと(行数ではない)

1本目・2本目を作って分かったのは、長さと面白さは別物だということ。
30分遊ばせるのは行数ではなく、次の4つ。

- **毎回違う**: 自動生成、ランダムな組み合わせ
- **少しずつ強くなる**: 手に入れたもので次の判断が変わる
- **段階的に見せる**: 3階で新しい敵、5階で新しい仕掛け、と小出しにする
- **納得できる負け方**: 理不尽ではなく「自分のミスだ」と分かる死に方にする

### 「AIのすごさ」として効くのは行数ではなく、手作業だと面倒なこと

devlog に書くと刺さるのはこういう話。行数の多さを自慢しても伝わらない。

- 自動生成した面を**総当たりで検証**してから出荷する(削除済みの「ひかりのかけら」でやった)
- **ライブラリなしで3Dを描く**(レイキャスティング、透視投影)
- **効果音を波形から合成**する(音声ファイルを1つも使わない)
- 生成した迷路が**必ずクリア可能だと確認**してから出す

### 遊ばせ方の選び方(毎回ここで決める)

オーナーから「遊ばせ方は任せる」と言われている。企画を決めたら、最初にこの表で形を選ぶ。

| 形 | 向いているジャンル | 必須の仕掛け |
|---|---|---|
| **短いプレイ × 何度も**(3〜5分 × 6〜10回) | アクション、シューティング、リズム、タイムアタック | 自己ベスト記録、毎回変わる要素、段階的に解放される要素 |
| **中くらい × 数回**(10〜15分 × 2〜3回) | ローグライク、物理 | 1周ごとに違う展開、周回で増える選択肢 |
| **長いプレイ × 1回**(30分前後) | 物語のあるもの、ステージ制の大作(土曜向き) | **途中保存(localStorage)が必須**。章ごとに区切りをつける |

どの形でも守ること:

- **最初の1分で面白さが伝わる。** Xから来た人は、最初の1分で閉じるかどうか決める。
  長いゲームほど、冒頭に見せ場を置く。
- **長いプレイには途中保存を入れる。** 30分を一気に遊べる人は少ない。
  閉じても続きから遊べないなら、それは30分のゲームではなく「30分遊ばないと終われないゲーム」になる。
- **通算30分の中身を devlog で説明できる。** 「何周するとこうなる」「何章まである」と具体的に言えること。

## 2026-09-28 「なげなわコメット」で分かったこと: テストが通っても、遊べるとは限らない

公式テスト(`npx playwright test`)は7件すべて通った。それなのに、**自動で25秒ぐるぐる回らせたら得点が0だった**。

原因は、しっぽの長さ(555px)がふつうの円の円周(半径110pxで691px)より短く、
一周する前にしっぽの先が消えて、永遠に交差しなかったこと。人間が遊んでも「回っているのに何も起きない」最悪の体験になっていた。

- 公式テストが見ているのは「エラーが出ないか」「必要な文字があるか」だけ。**面白いか、そもそも遊べるかは見ていない**。
- 直し方: しっぽを約900pxに延長。さらに「しっぽの古い部分に16px以内まで近づいたら輪にする」補助を入れた。
- バランスは、敵を追いかけて囲み、トゲと弾から逃げる自動プレイヤーを作って計測した。
  強化なしで約3.6分・ウェーブ9、強化MAXで約5分・ウェーブ11。強化しきるまで15回前後。
- 最初のボス(ウェーブ5)で一気にハートを失っていたので、弾を 12発/2.2秒 → 8発/2.8秒 に弱めた。
- ウェーブに制限時間を入れた。最後の1匹が捕まらずダラダラ続くのを防ぐため。

**教訓: 出荷前に、そのゲームの「核の遊び」が本当に機能しているかを、実際に操作して確かめる。**
数字(得点が入るか、ウェーブが進むか、何分で終わるか)で確認できると一番いい。

## 2026-09-29 テストのやり方を変えた(オーナー:「ちゃんとテストするように。なるべくやり切りたい」)

### 何を変えたか

- **`tests/play.spec.ts` を毎回書き直す。** 実際に操作して「遊べるか」を確かめるテスト。
  前のゲーム用のまま残っていると、ファイル名の照合で自動的に落ちる(書き直し忘れの防止)。
- ゲームには読み取り専用の窓口 `window.gameTest` を置く。テストはここから状態を読む。
- 修正の上限を **3回 → 10回**。5回で通らなければ、要素を削って簡単にする方向で直す。
- **テストを弱めて通すのは禁止**(期待値を下げる・消す・skip する)。
- 夜の自動実行の時間上限を **3時間 → 5時間**(`register_tasks.ps1`)。

夜の自動実行で許可されているのは git と `npx playwright test` だけなので、
自動プレイも計測も、すべて `play.spec.ts` の中でやる。別のスクリプトは動かせない。

### 「テストがある」だけでは足りなかった話

なげなわコメットで最初に書いたプレイテストは、**元のバグを戻しても通ってしまった**。
自動プレイヤーが敵のすぐ近くで小さな円(半径80px)を描いていたので、しっぽが短くても輪が閉じていた。
元のバグは「人がふつうに描く大きさの円」で起きていたので、見逃していた。

そこで「画面の短辺の10%・15%・20%の円を、人の手の速さ(毎秒400px)で描いて、輪が閉じるか」を直接確かめるテストを足した。
バグを戻すと半径78pxで「輪0個」となって**正しく落ち**、修正版では全部通ることを確認した。

**教訓: テストを書いたら、一度わざと壊して、本当に落ちるかを見る。** 落ちないテストは、無いのと同じ。
「人がふつうに操作する大きさ・速さ」で試すことも大事。テスト役の操作が器用すぎると、人がつまずく所を素通りする。
